# Independent Google fixtures

These are synthetic, hand-authored examples. They contain no account credentials or personal content. The test service does not depend on engine or protobuf crates and does not serialize production domain objects. HTTP conformance expectations are written before the Google adapter exists.

| Fixture / implementation | Source and behavior |
|---|---|
| `google/history-{page,final}.json` | [Gmail history list](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.history/list): sparse string IDs, separate page token, final history ID, label and deletion records. IDs exceed the exact integer range of JavaScript numbers. These literal wire examples are independent of the mock's generated token spelling. |
| `mime/multipart.eml`, `reply.eml`, `html-only.eml` | [Gmail Message resource](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages): raw MIME is base64url; payload parts, headers, attachment IDs, and internalDate/historyId use their documented types. Fixtures are stored as LF templates, substituted with synthetic account addresses, and converted to CRLF by the seed builder. Tests compare the returned raw bytes with independently constructed fixture bytes. |
| PDF MIME part | Original test bytes, not a downloaded document: a short PDF marker and synthetic payload. This fixture tests byte preservation, not PDF renderer validity. |
| `mime/reply-forward.eml` | [RFC 5322 §3.6.3–4](https://www.rfc-editor.org/rfc/rfc5322.html#section-3.6.4): grouped Reply-To, visible recipient arrays, Bcc exclusion, Message-ID/References. [RFC 2045 §5–6](https://www.rfc-editor.org/rfc/rfc2045.html#section-5): text attachment bytes retain Windows-1252 charset after quoted-printable decoding; multipart alternatives and inline Content-ID remain distinct. Independent mailparse/raw HTTP assertions expect `caf` followed by byte E9 and the eight-byte PNG signature, not UTF-8-normalized attachment content. |
| `calendar/canonical.json` | [Event resource](https://developers.google.com/workspace/calendar/api/v3/reference/events) and [events.list](https://developers.google.com/workspace/calendar/api/v3/reference/events/list): recurring master, moved occurrence, sparse cancelled exception, date-only exclusive end, TZID, and unknown-field retention. Fixed expectations cross Chicago's March 8, 2026 DST transition. Additional creation tests cross November 1. |
| `calendar/all-day-2.json` | Named two-day fixture from the approved plan. Provider ID `alldate02`; dates 2026-10-31 through exclusive 2026-11-02. Independent wire tests verify overlap on October 31 and November 1, including the Chicago offset change, and no overlap on November 2. Loaded explicitly per test; the base seed stays stable. |
| Conditional writes and effects | [events.insert](https://developers.google.com/workspace/calendar/api/v3/reference/events/insert) and [versioned resources](https://developers.google.com/workspace/calendar/api/guides/version-resources): client-generated base32hex IDs, duplicate IDs, If-Match, and explicit sendUpdates. If-Match is optional at the provider: omission is not silently protected by the mock. |
| OAuth | [Installed-app OAuth](https://developers.google.com/identity/protocols/oauth2/native-app): loopback redirect, state echo, S256 PKCE, one-use codes, refresh, expiry, scope denial, and invalid_grant. Only synthetic registrations are accepted. |
| Stable identity and scope aliases | [Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect): userinfo's stable, never-reused subject, verified email, and canonical userinfo.email scope spelling. The mock uses independently assigned subjects for the two synthetic accounts. Refresh rotation is optional simulated provider behavior, with real invalidation of the previous credential; no claim that Google always rotates is made. |

Sources checked September 10, 2026. OAuth codes and grants are independent state in the server; conformance requests use a separate raw HTTP client. The mock uses mailparse for MIME and rrule/chrono-tz for recurrence. The Google engine will consume Google wire responses and expanded instances; it must not reuse mock types or recurrence output as its expected result.

The history fixtures are examples, not captured live traffic. Passing these or the stateful service's tests does not establish live Google compatibility.
